Layout and Adaptive Behavior

本页

  • 1. Window size classes
  • 2. Page skeletons

Every MeoUI page adapts to the window it is given. Layout decisions are made from the window size class, never from the platform, the device name or a literal pixel width.

1. Window size classes

MeoWindowMetrics (width) reads MeoTheme.windowWidthSizeClass(). Widths are in dp before globalScale.

compact< 60016bottom bar (MeoNavigationBar)onephone, narrow window
medium600–83924rail (MeoNavigationRail)one, overlay secondarysmall tablet, half window
expanded840–119924sidebartwolaptop window
large1200–159932sidebartwo or threedesktop
extraLarge≥ 160040sidebartwo or threewide monitor

Height classes: compact < 480, medium < 900, expanded ≥ 900. A short window (landscape phone, split screen) hides secondary chrome first: large top bars collapse, hero areas shrink, bottom bars may become a rail.

Derived values from MeoWindowMetrics (instantiate it with availableWidth / availableHeight):

PropertyMeaning
pageMarginouter margin
sectionSpacinggap between sections (16 compact, 24 otherwise)
controlSpacinggap between controls (8 compact, 12 otherwise)
maximumContentWidthreadable width cap: 840 medium, 1040 expanded, 1200 large, 1440 extraLarge
navigationModebottomBar, rail or sidebar
usesOverlayPane / supportsTwoPanewhether a second pane overlays or sits beside
preferredColumnscard grid columns (1 compact, up to 2 medium, up to maxColumns otherwise; minimumColumnWidth 280)

Do not test width > 800. Test metrics.isCompactWidth, metrics.supportsTwoPane, metrics.preferredColumns.

2. Page skeletons

PatternUseAdaptive behavior
MeoAppLayoutAn app with a few top-level destinationsBottom bar / rail / sidebar from the class; Settings and About appended as routes (APP_SHELL.md)
MeoScaffoldA custom page host that needs explicit slots (topBar, navigationBar, navigationRail, sideSheet, fab, snackbar)Same navigation switch; you supply the parts
MeoPageLayoutA scrolling content page with a titleApplies pageMargin, section spacing, a single readable column; breakpoints compactWidth 680 / mediumWidth 920 / expandedWidth 1180
MeoListDetailLayoutA list and the detail of the selected itemTwo panes at supportsTwoPane; otherwise detail replaces the list (showDetail)
MeoSupportingPaneLayoutMain content plus a secondary pane (filters, inspector, task sheet)adaptiveMode: side-by-side when expanded, stacked when compact
MeoSettingsLayoutSettings with many categoriesCategory sidebar + detail; see SETTINGS.md

Choose by task, not by looks:

TaskPattern
Browse a catalog, open an itemMeoListDetailLayout (wide) / MeoPageHost route (compact)
Read or edit one long pageMeoPageLayout
Show something about the current page without leaving itMeoSupportingPaneLayout, MeoSideSheet
A short choice or confirmationDialog (DIALOGS.md), never a pane

3. Content width and columns

  • Reading and form pages: one column, centered, up to maximumContentWidth (and prose up to 560–680dp). Do not stretch a form across a 1600dp window.
  • Grids of cards: GridLayout with columns: metrics.preferredColumns. Columns are equal width; a card never has a fixed pixel width inside a grid.
  • Lists are full width of their column; a row is never narrower than its content needs.
  • Settings content ≈ 720–760dp wide (SETTINGS.md).

4. Regions of a page

┌───────────────────────────────────────────────┐
│ Top app bar  (title, ≤3 actions, overflow)     │  chrome
├────────┬──────────────────────────────┬───────┤
│ Nav    │ Header (title, subtitle,     │ Side  │
│ rail / │ primary action, tabs/chips)  │ sheet │
│ sidebar├──────────────────────────────┤ (opt) │
│        │ Content sections             │       │
│        │  section header              │       │
│        │  group / grid / list         │       │
├────────┴──────────────────────────────┴───────┤
│ Bottom bar (compact) · Snackbar above it       │
└───────────────────────────────────────────────┘

Rules:

  • The top app bar is chrome, not content. Page title lives in it (or the large bar's headline), not repeated in the body.
  • A section has a header (MeoListHeader), then one group, grid or list. Sections are separated by sectionSpacing, not by dividers.
  • A sticky action (Install, Save) lives in the header or a docked toolbar (MeoDockedToolbar), not floating over the text.
  • A FAB is for the single most common creation action of the page. A store has none.
  • Snackbars appear above the bottom bar, never over a primary action.

5. Scrolling

  • One scroll region per pane. Never nest vertical scroll areas.
  • Top bars may collapse on scroll (scrollProgress); a large bar collapses to small.
  • A long list uses MeoListView (keeps useMeoTransitions, scroll position with preserveScrollPosition).
  • Pull to refresh (MeoPullToRefresh) is for touch lists backed by remote data. On desktop provide a Refresh action as well.

6. Compact specifics

  • Bottom bar holds up to 5 destinations (compactNavigationLimit); more go to the sidebar modal via the overflow (openSidebar()).
  • Dialogs become bottom sheets or full-screen dialogs when content is tall.
  • A two-pane page becomes list → detail routes with a back arrow (MeoPageHost transitions).
  • Hover-only affordances do not exist; every action reachable by touch.

7. Checklist

  • ☐ Uses MeoWindowMetrics for margins, spacing and columns.
  • ☐ Verified at compact (360), medium (700), expanded (1000), large (1400).
  • ☐ No fixed widths on cards in a grid; no horizontal page scroll.
  • ☐ Content capped at maximumContentWidth.
  • ☐ One scroll region per pane.
  • ☐ Navigation switches by class, not by platform.
  • ☐ Safe-area margins honoured (SafeArea.margins, safeAreaTop/Bottom/Left/Right in MeoAppLayout).
